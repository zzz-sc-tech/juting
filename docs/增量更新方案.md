## v0.7.1 体积优化（2026-10-16）

在 Phase 1 分层基础上继续压缩，**安装体积与下载量双降**：

| 项 | 优化前 | 优化后 | 怎么做到的 |
|---|---:|---:|---|
| 安装目录 | 1.26 GB | **约 1.0 GB** | 依赖裁剪 + MySQL 调参 |
| `node_modules`（解压后） | 365 MB | **141 MB** | 按运行期依赖闭包白名单裁剪 |
| `-deps.zip`（下载量） | 123 MB | 约 55 MB | 同上 |
| MySQL 数据目录 | 219 MB | **约 140 MB** | redo 100M→32M、关 binlog |

**依赖裁剪**：前端与后台都以**预编译 dist** 提供服务，运行期不需要 React/antd/Vite/TypeScript
等构建期依赖。改为**白名单制**——从真正的运行入口（backend 的 dependencies、packages/*
的 dependencies、vite + @vitejs/plugin-react）出发递归展开依赖图，只保留闭包内的包
（332 个 → 含工作区包）。白名单优于黑名单：新装的无关依赖默认被排除，不会越漏越多。

⚠️ **实测踩到的三个坑（改裁剪逻辑前必读）**：
1. **作用域容器目录必须显式放行**：`node_modules/@colors`、`node_modules/@juting` 这类
   目录名（只有一段且以 `@` 开头）不是真实包名，会落到闭包判定被排除 → **整棵子树被切掉**。
   实测两次：`@juting/domain` 缺失、`@colors/colors` 缺失（winston 依赖它，后端直接崩）。
   修法：`segments.length === 1 && startsWith('@')` 直接放行。
2. **`vite preview` 会读 `vite.config.ts`**，两个 config 都 import `@vitejs/plugin-react`——
   它虽属构建期，却是「启动必需」。漏掉会让前端 preview 报 `UNRESOLVED_IMPORT` 并返回
   HTTP 000（**后端却是好的，容易误判成"裁剪没问题"**）。
3. **`vite` 8 顶层就 import `rolldown`**，缺了 preview 直接 `ERR_MODULE_NOT_FOUND`；
   `esbuild` 缺了仍正常（实测），但它本就在 vite 依赖里，会随闭包带上。

**MySQL 调参**（`start-all.mjs` 运行时生成 `my.ini`，故**存量用户下次启动即生效**，
无需重装）：`innodb_redo_log_capacity=32M`（默认 100MB，而库才 16MB）、`skip-log-bin`
（binlog 对单机自用无意义且持续增长）、临时表空间封顶 64M、buffer pool 256M→128M。
实测：redo 101MB→33MB，数据完好（38 门课程校验通过）。

**依赖门控改版**：原来用 `package-lock.json` 哈希做门控，但裁剪只改「打进包的内容」不改
lock → 老用户会判定「依赖没变」而拿不到裁剪版。改为：
- 清单新增 `deps.filesHash`（依赖包内文件清单 rel+size 的哈希）与 `deps.owned`（顶层包名清单）；
- 客户端比对本地标记文件 `temp/runtime/deps-state.json` 里的 `appliedHash`（更新器安装成功后写入）；
- 依赖层安装后**按 `deps.owned` 清理**本地多余的旧依赖（覆盖安装只覆盖不删除，
  不清理则老用户磁盘瘦不下来），`@juting/*` 永不删。

**分层归属调整**：工作区包（`node_modules/@juting/*`）从依赖层移到**程序层**——
它们是本仓库源码/dist，内容随代码变化；若留在依赖层，会出现「代码变了但第三方依赖没变
→ 依赖层被门控跳过 → @juting/* 更新不到」的漏更新。

**验证**（裁剪后真实启动，非静态检查）：
- 全栈启动跑通：数据库初始化 → 38 门课程导入 → 后端健康检查通过 → 学习端/管理端 HTTP 200
- 音频流实测：`/api/v1/media/objects?key=…ogg` 返回 HTTP 200 / `audio/ogg` / 5,745,593 字节
- 课程数据实测：`/api/v1/catalog` 与 `/api/v1/exercises/12` 返回完整元数据（含音频 URL、时长）
- 路径判定 `temp/layer-skip-test.mjs` **133/133**、flavor 路由回归 **12/12**

## 一、问题

桌面端每次「检查更新」都要下载完整的 `-update.zip`（六级 466MB）。而实际上一轮改动的
往往只是几 MB 的程序代码，音频（218MB）与依赖（120MB）根本没变。用户诉求：
**音频留在本地不动，只更新变化的部分。**

### 现状构成（v0.6.0 cet6 update.zip = 466MB，用 HTTP Range 拉尾部中央目录解析得出）

| 层 | 体积 | 文件数 | 变动频率 |
|---|---:|---:|---|
| `presets/cet6`（38×.ogg 音频 + 旁车 + seed + manifest） | **218.1 MB** | 85 | 极低（换内容才变） |
| `temp/runtime`（mysql 82 + node 35） | **121.9 MB** | 221 | **≈从不**（见下方死重 bug） |
| `node_modules`（运行期依赖） | **~120 MB** | ~44000 | 低（改 package-lock 才变） |
| 程序代码（backend/web-app/admin 的 dist+src、packages、scripts、seed.json、lock…） | **~3.4 MB** | — | **每次更新** |

> 程序代码 3.4MB 是实测：把 backend/src+dist、web-app/src+dist、admin/src+dist、packages、
> scripts、docs（除 HANDOFF）、根文档、句听.exe、jico、seed.json 用 deflate-1（与
> `make-update-zip.mjs` 同口径）压成一个 zip 的结果。

### 附带发现的 bug：temp/ 是纯死重

`launcher-app.cjs` 里 `UPDATE_PROTECTED = ['temp']` —— 覆盖安装时**整个 temp/ 被跳过**
（这是对的，temp/runtime 下住着 mysql-data / media-store 等用户数据）。但打包器
`package-release.mjs` 打 update.zip 时**把 temp/runtime/mysql 与 temp/runtime/node 也打了进去**
（它俩在 `temp/` 下）→ **每次更新白下 122MB，而且永远不会被应用**。

## 二、方案：三层分包 + 本地门控

### 2.1 资产拆分

| 资产 | 内容 | 大小 | 何时下载 |
|---|---|---:|---|
| `juting-v<版本>-win-full-cet6-update.zip` | 程序（含 seed.json，**排除 temp/**） | ~5 MB | **每次更新** |
| `juting-v<版本>-win-full-cet6-deps.zip` | `node_modules` + `deps-hash.txt` | ~120 MB | 仅依赖变化 |
| `juting-v<版本>-win-full-cet6-media.zip` | `presets/cet6/media/**` + 媒体清单 | ~218 MB | 仅音频变化 |

- **文件名不变**：程序包继续叫 `-update.zip`。老启动器（v0.6.0）按
  `pickFlavorAsset` 的 `-update.zip$` 优先规则会选中它 → 装上后启动器自身代码也更新了
  → 从下一个版本起才启用下面的门控。**零鸡生蛋问题。**
- `.7z` 完整包保持现状（含 temp/，全新安装要用），不动。

### 2.2 门控判据（关键设计）

```
程序包：总是下载（~5MB，无所谓）
deps 包：读包内 deps-hash.txt（= package-lock.json 的 sha256）
         与本地 temp/runtime/deps-hash.txt 比对；一致 → 跳过
media 包：比对「本地实际媒体文件」与「包内清单」
         一致 → 跳过；有差异 → 下载
```

**媒体门控为什么必须看实际文件、不能看本地 manifest.json**：
`presets/cet6/manifest.json` 会随程序包一起变新（它在 presets/ 下、被程序包覆盖），
所以「本地 manifest 说媒体已就位」在媒体其实缺失时会谎报。正确判据是遍历
`presets/<flavor>/media/**` 的实际文件集合（或抽查关键文件存在性）与包内清单比对。

实测成本：读 manifest 38 条算 sha256 = **2ms**，可忽略。

### 2.3 覆盖安装的语义（已验证安全）

`runApplyUpdate` 用 `fs.cpSync(staging, installDir, { force: true, filter })` 是**覆盖式
overlay，不删除包外文件**。所以：

- 程序包不含音频/依赖 → 安装后本地旧的音频/依赖**原样保留**，天然安全
- `temp/` 继续被保护（用户数据）
- 三道锚点校验（`package.json` / `句听.exe` / `start-all.mjs`）继续生效

### 2.4 与预设导入器的配合（无需改动）

`import-preset.mjs` 已有两条天然契合的机制：

1. **媒体「已存在跳过」**：`if (!fs.existsSync(target))` 才 link/copy，否则 `skipped++`
2. **按 seed_version 触发重导**：`local_preset_imports.seed_version === seed.version` 时快速跳过；
   版本不同才重导（opus seed 用 `-opus` 后缀，正是为此设计的）

所以「程序包带来新 seed.json + 媒体包带来新媒体」时，导入器会自动落位新媒体、
跳过已存在的旧媒体。

### 2.5 ⚠️ 硬链接陷阱（实测，v1 必须绕开）

媒体落位走 `fs.linkSync`（presets 侧 ←→ media-store 侧同一 inode）。本机实验证实：

```
初始: nlink=2, inode=A          （presets 与 media-store 共享）
cpSync 覆盖 presets 侧后:
   presets 侧 = NEW 内容, inode=B, nlink=1   ← 链接已断
   media-store 侧 = OLD 内容, inode=A         ← 仍是旧音频
```

**结论**：媒体包 v1 必须 **skip-if-exists（只补缺失文件，不覆盖已存在文件）**。
覆盖已有音频会导致「presets 是新的、media-store 还是旧的」分叉，播放走 media-store
→ 用户听不到新音频，而且没有任何报错。

若将来需要**替换**已有音频（换编码/纠错重制），必须走 relink 流程：
先删 media-store 侧（以及 presets 侧），再重新 link。列为 Phase 2。

## 四、边界与风险

| 风险 | 处置 |
|---|---|
| 媒体包下载到一半失败 | 复用现有 SHA256 校验 + 体积校验；失败则中止，本地媒体不受损（skip-if-exists 保证） |
| 用户手工删过部分媒体 | 门控比对发现差异 → 下媒体包 → skip-if-exists 只补缺失的那几个（不重下已有的） |
| 依赖升级但 deps 包漏发 | 锚点校验 + 启动失败可见；发布流程加检查（打包后核对三包齐全） |
| 老启动器（v0.5.0/v0.6.0）拿到新 release | 按 `-update.zip$` 选中程序包 → 正常升级 → 新启动器接管门控。`-deps.zip`/`-media.zip` 对老启动器不可见（资产名含 flavor token 但非 `-update.zip`/`.7z` 结尾，`pickFlavorAsset` 不会选） |
| 磁盘空间 | 媒体包只在需要时下；解压 staging 后 apply，峰值 ≈ 包体积 |
